# AGENTS.md

Единый источник правды для любого ИИ-агента (Claude Code, Codex, Cursor, Copilot и др.), который работает в этом репозитории. Прочитай файл целиком перед началом работы.

## 1. О проекте

Дашборд аналитики для продавца на Wildberries и Ozon. Портфолио-проект на синтетических данных, построенных по официальной документации API площадок.

Что умеет продукт:
- KPI: выручка, заказы, выкупы, % выкупа, возвраты, средний чек, прибыль, маржа, изменение к прошлому периоду;
- график продаж по дням с наложением прошлого периода, топ товаров;
- остатки на складах с предупреждением «скоро закончится» (дни запаса);
- страница заказов (~100 тыс. записей, виртуальная прокрутка);
- фильтры по периоду, маркетплейсу и категории (хранятся в URL), экспорт в Excel;
- светлая и тёмная тема, мобильная версия от 375 px.

Текущий статус и следующий шаг — в [docs/roadmap.md](docs/roadmap.md).

## 4. Архитектура — Feature-Sliced Design

```
src/
  app/       провайдеры (QueryClient, Router, Theme), глобальные стили, точка входа
  pages/     страницы: dashboard, orders, stocks
  widgets/   крупные блоки страницы: kpi-panel, sales-chart, top-products, stock-table, app-header
  features/  действия пользователя: filter-period, filter-marketplace, filter-category, export-excel, theme-toggle
  entities/  бизнес-сущности: sale, product, warehouse, marketplace (типы, zod-схемы, api-хуки, UI)
  shared/    переиспользуемое без бизнес-логики: ui, api, lib, styles, config
  mocks/     фейковый backend: генератор, адаптеры WB/Ozon, агрегаторы, MSW handlers
```

Правила:
- импорт только сверху вниз: `app → pages → widgets → features → entities → shared`; слайсы одного слоя не импортируют друг друга;
- доступ к слайсу только через его `index.ts` (public API);
- `mocks/` изображает backend: UI-слои не импортируют из `mocks/` ничего, кроме точки запуска MSW в `app/`;
- клиент получает от API только агрегаты и страницы таблиц, никогда — все сырые записи.

Подробности — [ADR-0003](docs/adr/0003-feature-sliced-design.md).

## 5. Процесс работы над фичей

1. **Spec.** Создать `docs/specs/NNN-название.md` по [шаблону](docs/specs/_шаблон.md). Показать пользователю, дождаться согласования.
2. **Тесты.** Вызвать субагента `qa`: он пишет тесты по критериям приёмки, не видя реализации. Тесты красные.
3. **Код.** Реализовать фичу до зелёных тестов.
4. **Ревью.** Вызвать субагента `reviewer` (архитектура, конвенции, безопасность). Исправить замечания.
5. **Документация.** Обновить spec (статус), ADR (если принято архитектурное решение), `docs/roadmap.md`, этот файл (если изменились команды или правила).
6. **Коммит** — строго по разделу 6.

Skill `new-feature` проводит по этому процессу.

## 6. Git

- Модель веток — **GitHub Flow** ([ADR-0012](docs/adr/0012-github-flow.md)): `main` всегда рабочая; на каждую задачу короткая ветка `feat/…`, `fix/…`, `docs/…`, `chore/…`, `test/…`; в `main` напрямую не коммитим.
- Сообщения коммитов — Conventional Commits, тип на английском, описание на русском: `feat: добавить KPI-карточки`.
- **Перед каждым коммитом** показать пользователю:
  1. имя ветки;
  2. список изменённых файлов;
  3. текст коммита;
  4. объяснение простыми словами: что сделано и зачем;
  5. как проверить руками.
- Коммит — только после явного «ок» пользователя. Push, merge и PR — тоже только с согласия.
- Изменения готовить небольшими порциями, удобными для ручного просмотра.

## 7. Роли ИИ

Один основной агент (планирует, пишет код, общается с пользователем) и два субагента в `.claude/agents/` ([ADR-0011](docs/adr/0011-роли-ии.md)):

| Субагент | Когда вызывать | Что делает |
|---|---|---|
| `qa` | после согласования spec, до кода | пишет тесты по критериям приёмки |
| `reviewer` | перед показом коммита пользователю | проверяет FSD, конвенции, читаемость, безопасность |

Каждый вызов субагента и его итог озвучиваются пользователю. Субагенты не коммитят и не обходят раздел 6. Новая роль заводится только под реальную проблему, через ADR.

## 8. Работа с контекстом

- Одна фича — один чат. Всё долговременное хранится в репозитории (этот файл, ADR, spec, roadmap), а не в переписке.
- Когда фича закоммичена: обновить `docs/roadmap.md` и сказать пользователю «Фича закрыта, можно начинать новый чат (`/clear`)».
- Новый чат начинается с чтения этого файла и `docs/roadmap.md`.
- Если чат разросся посреди фичи — предложить пользователю `/compact`.

## 9. Конвенции кода

- Язык: документация, комментарии, тексты UI и коммитов — на русском; идентификаторы — на английском.
- TypeScript строгий, без `any`; внешние данные (URL, ответы API) проверяются zod-схемами.
- Компоненты — функции, один компонент на файл, стили рядом: `Component.tsx` + `Component.module.css`.
- Цвета, отступы, радиусы и шрифты — только через токены из `src/shared/styles/tokens.css`, без «магических» значений.
- Числа, деньги и даты — только через форматтеры из `shared/lib` (локаль ru-RU).
- У каждого блока с данными есть состояния: загрузка (скелетон), пусто, ошибка.
- Комментарий объясняет «зачем», а не «что».

## 10. Безопасность

Подробно — [docs/security.md](docs/security.md). Обязательный минимум:
- никаких секретов в клиентском коде и в git; всё с префиксом `VITE_*` публично; файлы `.env*` не читать и не коммитить;
- не использовать `dangerouslySetInnerHTML`;
- ячейки экспорта в Excel экранируются от formula injection;
- пакет `xlsx` из npm не использовать;
- новая зависимость — только через ADR и после объяснения пользователю.

## 11. Definition of Done

Фича готова, когда:
- [ ] spec согласована, все критерии приёмки покрыты тестами;
- [ ] `npm run lint`, проверка типов, steiger и тесты проходят;
- [ ] есть состояния загрузки, пусто, ошибка; вёрстка проверена на 375 px и десктопе в обеих темах;
- [ ] ревью субагента `reviewer` пройдено;
- [ ] документация обновлена (spec, ADR, roadmap);
- [ ] пользователь проверил изменения и дал «ок» на коммит.

## 13. Правила проекта

Правила, которые пользователь добавляет по ходу работы. Раздел только дополняется (append-only); отменённое правило зачёркивается с пометкой, а не удаляется. Новое правило добавляется через skill `add-rule`.

1. **2026-11-04 — CI/CD и внешние сервисы только с объяснением.** Всё, что связано с CI/CD (GitHub Actions, npm audit, gitleaks, Dependabot), GitHub, Vercel, внешними сервисами и настройками ИИ (`.claude/settings.json`), делается только после объяснения простыми словами (что это, зачем, что изменится) и явного согласия пользователя.
   *Причина:* пользователь не знаком с CI/CD и хочет понимать каждый шаг.
2. **2026-11-04 — Коммит только после ручной проверки.** Перед каждым коммитом показывать ветку, файлы, текст коммита, объяснение и способ проверки (раздел 6). Коммит, push, merge, PR — только после «ок».
   *Причина:* ответственный проект; пользователь сам разбирается в каждом изменении.
3. **2026-11-04 — Работаем по GitHub Flow, без ветки `dev`.**
   *Причина:* один разработчик, постоянный деплой; роль промежуточной проверки выполняют превью-деплои Vercel.
4. **2026-11-04 — Чтение без спроса, остальное с разрешением.** Команды чтения внутри проекта (`ls`, `cat`, `grep`, `git status/diff/log/show` и т.п.) выполняются без подтверждения. Запуск скриптов, установка пакетов, изменения git и удаление файлов — только с разрешения. Файлы `.env*` не читаются. Закреплено в `.claude/settings.json`.
   *Причина:* экономия времени при сохранении контроля; пользователь не доверяет автоматическому запуску скриптов.
5. **2026-11-04 — Одна фича — один чат.** После закрытия фичи обновить roadmap и предложить пользователю начать новый чат (раздел 8).
   *Причина:* длинный контекст ухудшает качество работы агента.
