# Новая фича

Процесс из AGENTS.md, раздел 5. Ни один шаг не пропускается без явного разрешения пользователя.

## 1. Подготовка
1. Прочитать `AGENTS.md`, `docs/roadmap.md`, `docs/domain.md` и ADR, относящиеся к фиче.
2. Определить номер spec: следующий свободный в `docs/specs/`.
3. Создать ветку `feat/<короткое-имя>` от актуальной `main` — команду показать пользователю.

## 2. Spec
1. Скопировать `docs/specs/_шаблон.md` в `docs/specs/NNN-<имя>.md`, заполнить.
2. Критерии приёмки — проверяемые, по одному утверждению, с номерами AC-1, AC-2…
3. Обязательно заполнить «Состояния», «Безопасность», «Не входит в задачу».
4. Показать spec пользователю простым языком. **Остановиться и дождаться согласования.** Статус → «согласовано».

## 3. Тесты (субагент `qa`)
1. Вызвать субагента `qa`, передав путь к spec. Код реализации ему не показывать.
2. Сообщить пользователю: какие тесты написаны, какие AC они покрывают.
3. Убедиться, что тесты падают по правильной причине (нет реализации), а не из-за ошибки в самом тесте.

## 4. Реализация
1. Писать код по FSD (AGENTS.md, раздел 4), конвенциям (раздел 9) и токенам.
2. Не менять тесты `qa`, чтобы они «прошли». Если тест неверен — объяснить пользователю и исправить с его согласия.
3. Довести до зелёных тестов, линтера, проверки типов и steiger.

## 5. Ревью (субагент `reviewer`)
1. Вызвать `reviewer` с описанием фичи и путём к spec.
2. Исправить замечания уровня «блокер» и «важно». Остальные — пересказать пользователю.

## 6. Документация
- spec: статус «готово», колонка «Тест» заполнена;
- ADR: новый, если принято архитектурное решение (skill `new-adr`);
- `docs/roadmap.md`: отметить пункт, указать следующий шаг;
- `AGENTS.md`: если изменились команды или структура.

## 7. Коммит
Показать пользователю (AGENTS.md, раздел 6): ветку, файлы, текст коммита, объяснение «что и зачем», как проверить руками. Коммит — только после «ок». Затем предложить слияние в `main` и новый чат (раздел 8).
