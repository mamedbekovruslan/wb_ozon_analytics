# 001. Фейковый API: сверка WB/Ozon, генератор, адаптеры, эндпоинты

- **Статус:** готово
- **Дата:** 2026-11-05
- **Ветка:** `feat/mock-api`
- **Связанные ADR:** [0004](../adr/0004-msw-и-генератор-данных.md), [0009](../adr/0009-стратегия-тестирования.md), [0010](../adr/0010-контракт-api-и-адаптеры.md), [0003](../adr/0003-feature-sliced-design.md)

## Цель

У дашборда нет данных: сейчас фейковый backend отвечает только `/api/health`. Фича создаёт «магазин» на синтетических данных, похожих на настоящие выгрузки WB и Ozon, и отдаёт по нашему контракту `/api/...` всё, что нужно экранам из макетов: KPI, ряд по дням, топ товаров, остатки, страницы заказов. Интерфейса в фиче нет — виджеты делаются следующими фичами поверх готового API.

## Пользовательские сценарии

- Как продавец, я хочу видеть в демо правдоподобные цифры (разный % выкупа у одежды и электроники, FBO/FBS у Ozon, сезонность), чтобы дашборд выглядел как настоящий инструмент.
- Как разработчик следующих фич, я хочу готовый проверенный API с zod-контрактом, чтобы делать только интерфейс.
- Как автор портфолио, я хочу показать, что данные построены по документации API площадок, а переход на реальный backend не требует переписывать UI.

## Как устроено (кратко, по ADR-0010)

```
генератор (seed) ──► сырые записи в форме API WB / Ozon
                         │
            wbAdapter / ozonAdapter ──► единая доменная модель (заказ, событие, остаток)
                         │
                    агрегаторы ──► MSW handlers /api/... ──► zod-схемы в entities/* (клиент)
```

Порядок работы внутри фичи:
1. **Сверка** с актуальной документацией (dev.wildberries.ru, docs.ozon.ru) → `docs/domain/wb-api.md`, `docs/domain/ozon-api.md`: дата, ссылки, используемые эндпоинты и поля, таблица соответствия полей доменной модели, допущения. Показывается пользователю до тестов: от неё зависят тесты адаптеров.
2. Тесты от `qa` по этой spec и документам сверки.
3. Генератор → адаптеры → агрегаторы → handlers → zod-схемы в `entities/*`.

## Критерии приёмки

«Сегодня» — дата, от которой генератор строит данные (в приложении — текущая дата по Москве, в тестах — фиксированная). Все даты — календарные дни по Москве, границы периода `from`/`to` включительно.

## Состояния

UI в фиче нет, поэтому состояния — на уровне API:
- Загрузка: handlers отвечают с небольшой случайной задержкой (`delay()` MSW: в браузере — «реалистичная», в тестах — почти мгновенная), чтобы будущие виджеты показывали скелетоны.
- Пусто: валидный запрос без данных (например, категория без продаж за период) → 200 с нулями, `null` в долях и пустыми списками, а не ошибка.
- Ошибка: невалидные параметры → 400 (AC-24); неожиданная форма ответа ловит `apiGet` + zod на клиенте (уже есть).

## Дизайн и адаптивность

- Макетов на фичу нет: интерфейса не появляется. Временная страница дашборда меняет только источник проверки «Фейковый API: работает».
- Данные подобраны под макеты: 8 категорий, склады WB (Коледино, Электросталь, Подольск, Казань, Краснодар, Екатеринбург, Тула, Новосибирск) и Ozon (Хоругвино, Пушкино, Гривно, Казань, Новосибирск FBO + склад продавца FBS), названия и артикулы товаров из `reference/*.dc.html` входят в каталог.

## Данные и API

Все эндпоинты — `GET`. Общие параметры фильтров: `from`, `to` (`ГГГГ-ММ-ДД`), `mp` (`all` | `wb` | `ozon`, по умолчанию `all`), `cat` (повторяемый, id категории; нет — все).

| Эндпоинт | Параметры | Что отдаёт |
|---|---|---|
| `/api/meta` | — | категории (id + название), площадки, «сегодня», время обновления, начало истории |
| `/api/kpi` | фильтры | метрики текущего и прошлого периода + sparkline по 14 точек |
| `/api/sales-daily` | фильтры | по дням: WB и Ozon × (выручка, заказы, прибыль) + итог дня прошлого периода |
| `/api/top-products` | фильтры, `sort` (`revenue` \| `orders` \| `buyoutRate` \| `profit`), `limit` ≤ 50 | товар, артикул, площадка, категория, выручка, заказы, % выкупа, прибыль |
| `/api/stocks` | `mp`, `cat`, `status`, `limit` | на дату: товар × склад (FBO/FBS у Ozon), остаток, скорость, дни запаса, статус; счётчики по статусам |
| `/api/orders` | фильтры, `q`, `status`, `sort`, `dir`, `offset`, `limit` ≤ 200 | страница заказов (дата и время, номер, товар, артикул, площадка, склад, сумма, статус), всего найдено, счётчики по статусам |

- Точные поля ответов — раздел «Контракт» ниже; zod-схемы — в `entities/*`.
- `mocks/` не импортирует `entities/*` (backend не знает о клиенте); совпадение ответов со схемами доказывают тесты (AC-23).
- Себестоимости в API площадок нет — генератор создаёт её как «справочник продавца» по каждому SKU.
- Фото товаров в API нет: превью в макетах — забота виджетов.

## Контракт (для реализации и тестов)

Записан до тестов: `qa` пишет тесты по нему, не видя кода (ADR-0011). Даты — строки `ГГГГ-ММ-ДД` (день по Москве), моменты времени — ISO 8601 с `+03:00`. Деньги — рубли, число. Доли (`buyoutRate`, `margin`) — проценты 0–100.

### Справочники

- Категории (`CategoryId` → название): `shoes` Обувь, `clothing` Одежда, `electronics` Электроника, `beauty` Красота, `home` Дом и кухня, `sports` Спорт, `kids` Детские товары, `accessories` Аксессуары.
- Площадки: `wb` WB, `ozon` Ozon. Каждый товар каталога продаётся на одной площадке.
- Фильтры (`Filters`): `{ from, to, mp: 'all' | 'wb' | 'ozon', cat: CategoryId[] }`; в URL `cat` повторяется (`?cat=shoes&cat=sports`).

### Модули `src/mocks/` (публичные функции для тестов)

| Модуль | Экспорт | Что делает |
|---|---|---|
| `mocks/generator` | `generateRawData({ seed: number, today: string }): RawData` | сырые данные: `{ catalog, wb: { orderFeed, salesReport, stocks }, ozon: { fboPostings, fbsPostings, returns, accruals, fboStocks, fbsStocks, statusLog } }` — элементы массивов в форме API из `docs/domain/*` |
| `mocks/wb` | `wbRawSchemas` (`orderFeedOrder`, `salesReportRow`, `stockItem`), `wbAdapter(raw: RawData['wb'], catalog)` | zod-схемы сырого формата WB; адаптер → `{ orders: Order[], stocks: StockRow[] }` |
| `mocks/ozon` | `ozonRawSchemas` (`fboPosting`, `fbsPosting`, `returnItem`, `accrual`, `fboStockItem`, `fbsStockItem`, `statusLogEntry`), `ozonAdapter(raw: RawData['ozon'], catalog)` | то же для Ozon |
| `mocks/aggregators` | `kpi(orders, filters)`, `salesDaily(orders, filters)`, `topProducts(orders, filters, { sort, limit })`, `stocks(stockRows, orders, { today, mp, cat, status?, limit? })`, `ordersPage(orders, query)` | метрики по формулам `docs/domain.md`; результат — тела ответов `/api/...` |

Доменные типы (`mocks/domain`):

```ts
type Outcome = 'inTransit' | 'bought' | 'cancelled' | 'returned'
type Order = {
  id: string; marketplace: 'wb' | 'ozon'; scheme: 'FBO' | 'FBS' | null
  sku: string; offerId: string; name: string; category: CategoryId; warehouse: string
  orderedAt: string            // ISO с +03:00
  orderDate: string            // ГГГГ-ММ-ДД по Москве
  price: number
  outcome: Outcome
  boughtOn: string | null      // день выкупа (есть и у returned)
  cancelledOn: string | null
  returnedOn: string | null
  commission: number           // удержана при выкупе, 0 если выкупа не было
  commissionRefund: number     // возвращена при возврате, иначе 0
  costPrice: number            // себестоимость единицы из справочника продавца
  logistics: { date: string; amount: number }[]   // каждое списание за доставку — своим днём
}
type StockRow = {
  sku: string; offerId: string; name: string; category: CategoryId
  marketplace: 'wb' | 'ozon'; scheme: 'FBO' | 'FBS' | null; warehouse: string; stock: number
}
```

Скорость продаж пары «товар × склад» = число заказов с этим `sku` и `warehouse`, у которых `boughtOn` в последних 14 днях **включая** «сегодня», / 14. Sparkline: день периода с индексом `i` (от 0) из `n` дней попадает в точку `floor(i × 14 / n)`; при `n < 14` — точка на день.

`Metrics` = `{ ordersCount, ordersSum, buyoutsCount, revenue, buyoutRate | null, returnsCount, returnsSum, avgCheck | null, commission, logistics, costPrice, profit, margin | null }`.

| Эндпоинт | Тело ответа 200 |
|---|---|
| `/api/meta` | `{ today, updatedAt, historyFrom, marketplaces: { id, name }[], categories: { id, name }[] }` |
| `/api/kpi` | `{ period: { from, to }, previousPeriod: { from, to }, current: Metrics, previous: Metrics, sparklines: { [ключ Metrics]: (number \| null)[] } }` |
| `/api/sales-daily` | `{ days: { date, wb: Day, ozon: Day, total: Day, previousDate, previousTotal: Day }[] }`, где `Day = { revenue, ordersCount, profit }` |
| `/api/top-products` | `{ items: { sku, name, offerId, marketplace, category, revenue, ordersCount, buyoutRate \| null, profit }[] }` |
| `/api/stocks` | `{ asOf, total, counts: { critical, soon, ok, noSales }, items: { sku, name, offerId, marketplace, scheme, warehouse, category, stock, perDay, days \| null, status: 'critical' \| 'soon' \| 'ok' \| 'noSales' }[] }` — `counts` не зависят от фильтра `status` |

### Уточнения после вопросов `qa` (2026-11-05)

1. **Изменение к прошлому периоду** в `/api/kpi` не отдаётся: клиент считает его из `current` и `previous` готовым `changePercent` из `shared/lib` (он уже возвращает `null` при прошлом = 0). Из AC-14 этот пункт уходит в фичу KPI-карточек.
2. **Справочник продавца** (`catalog`) — массив `{ sku, offerId, name, category, marketplace, costPrice }`.
3. **Склад продавца Ozon** (`warehouse_id` → «Склад продавца, Москва») — константа BFF в `mocks/ozon`, как настройка магазина; в `RawData` отдельного списка нет.
4. **WB, строки логистики** имеют `docTypeName = «Продажа»`, как строка продажи; выкуп — строка, где и `docTypeName`, и `sellerOperName` = «Продажа».
5. **Одна цена.** `Order.price` = `sellerPrice` (WB) / `products[].price.amount` (Ozon); заказы ₽, выручка и возвраты ₽ считаются по ней.
6. **Ozon, начисления:** продажа — начисление с `sale_price > 0`; начисление с одной логистикой — `sale_price = "0.00"`.
7. **Сырые типы:** у WB `cancelType` есть только у `cancel`; у Ozon `accrual_id` — строка, `financial_data.products[].price`/`old_price`/`payout` — числа, валюта `RUB`. Сырые zod-схемы описывают только используемые поля (лишние отбрасываются).
8. **`ordersPage`**: все параметры `query` необязательны; нет `status` — все; по умолчанию `sort = date`, `dir = desc`, `offset = 0`, `limit = 50`. `topProducts` по умолчанию — 10 по выручке.
9. **Sparkline для долей** (`buyoutRate`, `avgCheck`, `margin`) — метрика, посчитанная по своему отрезку (может быть `null`).
10. **`/api/stocks`, `total`** — число позиций после всех фильтров (`mp`, `cat`, `status`) до `limit`.
11. **Поиск заказов** — по названию, `offerId`, `sku` и номеру заказа, без учёта регистра.
12. **`/api/stocks`** не принимает период: `from`/`to` молча игнорируются.
13. **Параметры 400:** несуществующая дата (`2026-02-30`), отсутствие или пустое значение `from`/`to` у эндпоинтов с периодом → 400. ~~`from` раньше начала истории допустим (за те дни — нули).~~ Изменено 2026-11-05 по ревью (решение пользователя): `from` раньше `historyFrom` → 400 «За это время данных нет» — иначе ряд по дням разрастается до сотен тысяч точек, а в фиче 2 период придёт из ссылки. Прошлый период BFF считает сам и может выходить за начало истории (за те дни — нули). Пустое значение любого необязательного параметра (`?limit=`) — как его отсутствие. Непредвиденная ошибка BFF → 500 с `{ message }` без стека.
14. **История:** `historyFrom` = «сегодня» минус 24 месяца (05.11.2026 → 05.11.2024), первый заказ — в этот день; `updatedAt` = момент `now`, переданный в `createHandlers`.
15. **«Старше 30 дней»** (AC-6) — дата заказа раньше «сегодня − 30 дней».
16. **WB `cancelType = other`** — как `app`: логистики нет.
17. **Ozon, несколько товаров в отправлении:** ~~каждая единица — отдельный заказ; `posting_number/1`, `/2`…~~ Изменено 2026-11-05 по ревью: правило деления логистики, комиссии и возврата между единицами не описано, поэтому адаптер на отправлении с несколькими единицами бросает ошибку. Генератор таких отправлений не создаёт; правило — когда понадобятся реальные данные.
18. **«Сейчас».** `generateRawData` принимает необязательный `now`: заказы и события позже него ещё не наступили (утром нет вечерних заказов). Без `now` — весь день «сегодня»; `createHandlers` передаёт свой `now`. Заказы с `now` — ровно те же заказы, что без `now`, оформленные не позже `now` (те же номер, товар, цена, склад, время). Событие, наступающее позже `now`, ещё не произошло: нет ни смены статуса, ни строк отчёта реализации WB, ни начислений и возвратов Ozon.
19. **Объём во времени.** Тренд роста магазина выходит на плато после 05.11.2026: окно истории сдвигается за реальной датой, и без плато через ~10 месяцев объём вышел бы за 90–110 тыс. (AC-3).

Zod-схемы ответов: `entities/marketplace` — `metaResponseSchema`; `entities/sale` — `kpiResponseSchema`, `salesDailyResponseSchema`, `ordersResponseSchema`; `entities/product` — `topProductsResponseSchema`; `entities/warehouse` — `stocksResponseSchema`.

## Безопасность

- **T4** — параметры запросов проверяются zod в handlers, мусор → 400, а не падение (AC-24).
- **T5** — ответы проверяются схемами контракта на клиенте (`apiGet`), это же проверяют тесты (AC-23).
- **T1** — токенов и секретов нет: данные синтетические, реальные API не вызываются.
- Сообщения об ошибках без технических деталей (чек-лист `docs/security.md`).
- Новых зависимостей нет: PRNG пишется сам (несколько строк), даты — встроенный `Date`/`Intl`.

## Не входит в задачу

- Виджеты, хуки TanStack Query, скелетоны и любой новый UI — фичи 3–7.
- Фильтры в URL и их значения по умолчанию — фича 2.
- Web Worker для генерации — только если замер покажет > 100 мс блокировки на запрос (ADR-0004), отдельным решением.
- Экспорт в Excel (фича 8), реальные API WB/Ozon, авторизация.
- Реклама, хранение, штрафы, налоги — в прибыли не учитываются (`docs/domain.md`).

## Замеры

Цель ADR-0004 — < 100 мс на запрос. Замер 2026-11-05: `npx vitest bench --run src/mocks/perf.bench.ts` (Node, среда Vitest; в собранном приложении обычно быстрее), «сегодня» 05.11.2026, ~100 тыс. заказов.

| Что | Среднее |
|---|---|
| Первая генерация + адаптеры (один раз при первом запросе) | **~2 700 мс** — выше цели |
| `/api/stocks` | 11 мс |
| `/api/kpi`, 30 дней / год | 27 / 36 мс |
| `/api/top-products`, 30 дней | 28 мс |
| `/api/sales-daily`, год | 37 мс |
| `/api/orders`, год с поиском / вся история | 42 / 77 мс |

**Решение (пользователь, 2026-11-05):** эндпоинты укладываются в цель; первая генерация блокирует вкладку ~2,7 с — по ADR-0004 переносится в Web Worker **отдельной задачей до фичи «KPI-карточки»** (свой ADR, spec, тесты). В этой фиче не делается: интерфейса с данными пока нет.

## Решения (согласовано 2026-11-05)

- **История 24 месяца вместо 18** при том же объёме ~100 тыс. заказов: пресет «Год» со сравнением требует 2 года данных. Уточнить ADR-0004.
- **Данные «едут» за реальной датой:** каждый день строится от seed + дата, поэтому одна и та же дата всегда даёт одни и те же заказы (AC-2), а окно истории сдвигается вместе с сегодняшним днём.
- **Порядок коммитов:** одна ветка, три коммита, каждый показывается отдельно: (1) сверка `docs/domain/`; (2) генератор + адаптеры; (3) агрегаторы + handlers + схемы в `entities` + уборка `/api/health`. PR — один, в конце.
