# 001. Фейковый API: сверка WB/Ozon, генератор, адаптеры, эндпоинты

- **Статус:** в работе
- **Дата:** 2026-11-05
- **Ветка:** `feat/mock-api`
- **Связанные ADR:** [0004](../adr/0004-msw-и-генератор-данных.md), [0009](../adr/0009-стратегия-тестирования.md), [0010](../adr/0010-контракт-api-и-адаптеры.md), [0003](../adr/0003-feature-sliced-design.md)

## Цель

У дашборда нет данных: сейчас фейковый backend отвечает только `/api/health`. Фича создаёт «магазин» на синтетических данных, похожих на настоящие выгрузки WB и Ozon, и отдаёт по нашему контракту `/api/...` всё, что нужно экранам из макетов: KPI, ряд по дням, топ товаров, остатки, страницы заказов. Интерфейса в фиче нет — виджеты делаются следующими фичами поверх готового API.

## Пользовательские сценарии

- Как продавец, я хочу видеть в демо правдоподобные цифры (разный % выкупа у одежды и электроники, FBO/FBS у Ozon, сезонность), чтобы дашборд выглядел как настоящий инструмент.
- Как разработчик следующих фич, я хочу готовый проверенный API с zod-контрактом, чтобы делать только интерфейс.
- Как автор портфолио, я хочу показать, что данные построены по документации API площадок, а переход на реальный backend не требует переписывать UI.

## Как устроено (кратко, по ADR-0010)

```
генератор (seed) ──► сырые записи в форме API WB / Ozon
                         │
            wbAdapter / ozonAdapter ──► единая доменная модель (заказ, событие, остаток)
                         │
                    агрегаторы ──► MSW handlers /api/... ──► zod-схемы в entities/* (клиент)
```

Порядок работы внутри фичи:
1. **Сверка** с актуальной документацией (dev.wildberries.ru, docs.ozon.ru) → `docs/domain/wb-api.md`, `docs/domain/ozon-api.md`: дата, ссылки, используемые эндпоинты и поля, таблица соответствия полей доменной модели, допущения. Показывается пользователю до тестов: от неё зависят тесты адаптеров.
2. Тесты от `qa` по этой spec и документам сверки.
3. Генератор → адаптеры → агрегаторы → handlers → zod-схемы в `entities/*`.

## Критерии приёмки

«Сегодня» — дата, от которой генератор строит данные (в приложении — текущая дата по Москве, в тестах — фиксированная). Все даты — календарные дни по Москве, границы периода `from`/`to` включительно.

### Генератор

| № | Критерий | Тест |
|---|---|---|
| AC-1 | Если запустить генератор дважды с одинаковыми seed и «сегодня», данные совпадают полностью. | |
| AC-2 | Заказы, оформленные в день D, одинаковы (номера, товары, цены, склады) при любом «сегодня» позже D; меняться может только их статус (заказ, оформленный вчера, ещё в пути, а через месяц — завершён). | |
| AC-3 | Объём: история за 24 месяца до «сегодня», 90–110 тыс. заказов, 380–420 SKU, 8 категорий из макета (Обувь, Одежда, Электроника, Красота, Дом и кухня, Спорт, Детские товары, Аксессуары), обе площадки, не меньше 10 складов. | |
| AC-4 | % выкупа за всю историю (по формуле `docs/domain.md`) у категории «Одежда» — 30–60 %, у «Электроника» — 85–95 %. | |
| AC-5 | У Ozon есть отправления и FBO, и FBS; у WB все заказы со склада WB (`isMp = false`), схема в доменной модели — `null` (как в макетах). | |
| AC-6 | Ни одно событие (заказ, выкуп, отмена, возврат) не позже «сегодня»; среди заказов последних 7 дней есть незавершённые («в пути»), заказы старше 30 дней все завершены. | |
| AC-7 | Каждая сырая запись WB проходит zod-схему сырого формата по `docs/domain/wb-api.md`. | |
| AC-8 | Каждая сырая запись Ozon проходит zod-схему сырого формата по `docs/domain/ozon-api.md`. | |

### Адаптеры

| № | Критерий | Тест |
|---|---|---|
| AC-9 | `wbAdapter` преобразует сырые записи WB в доменную модель по таблице соответствия из `docs/domain/wb-api.md`; каждая строка таблицы (статусы, цена, комиссия, логистика, склад, артикулы, даты) проверена на примере записи. | |
| AC-10 | `ozonAdapter` — то же по `docs/domain/ozon-api.md`, включая FBO/FBS и перевод времени из UTC в московское (отправление в 22:30 UTC относится к следующему дню по Москве). | |
| AC-11 | Обе площадки дают записи одного доменного типа, отличающиеся только полем площадки `wb` / `ozon`. | |

### Агрегаторы (формулы — `docs/domain.md`)

| № | Критерий | Тест |
|---|---|---|
| AC-12 | KPI на ручном наборе из нескольких заказов совпадают с расчётом по формулам: заказы (шт и ₽), выкупы, выручка, % выкупа, возвраты (шт и ₽), средний чек, комиссия, логистика, себестоимость, прибыль, маржа. | |
| AC-13 | Учёт — по «Двум правилам учёта» `docs/domain.md`: счётчики и деньги относятся к дню события (заказ — к дате заказа; выручка, комиссия, логистика, себестоимость — к дню выкупа, отмены или возврата; при возврате выручка, комиссия и себестоимость вычитаются, логистика — нет); % выкупа — по итогу заказов, оформленных в периоде. Пример с курткой из `domain.md` даёт ровно указанные там суммы по дням. | |
| AC-14 | `null`, а не 0 и не `NaN`: средний чек — если нет выкупов; % выкупа — если нет завершённых заказов; маржа — если выручка ≤ 0; изменение к прошлому периоду — если прошлое значение 0. | |
| AC-15 | Прошлый период — той же длины и непосредственно перед текущим (для 05.10–03.11 это 05.09–04.10). | |
| AC-16 | Фильтры площадки и категорий применяются ко всем агрегатам; пустой список категорий = все категории. | |
| AC-17 | Ряд по дням содержит ровно одну точку на каждый день периода, включая дни без продаж (нули); для каждой метрики (выручка, заказы, прибыль) WB + Ozon = итог дня; ряд прошлого периода той же длины. | |
| AC-18 | KPI содержат sparkline из 14 точек на каждую метрику: период делится на 14 равных отрезков (если в периоде меньше 14 дней — точка на день). | |
| AC-19 | Топ товаров: N товаров с наибольшим значением выбранной метрики (выручка, заказы, % выкупа, прибыль), по убыванию; по умолчанию — 10 по выручке. | |
| AC-20 | Остатки: скорость продаж = выкупы за последние 14 дней до «сегодня» / 14 по каждой паре «товар × склад»; дни запаса и статус — по `docs/domain.md`; фильтр по периоду на остатки не действует. | |
| AC-21 | Остатки отсортированы по дням запаса по возрастанию, «нет продаж» — в конце; ответ содержит число позиций в каждом статусе. | |
| AC-22 | Заказы: страница по `offset`/`limit`, общее число найденных, по умолчанию сортировка по дате по убыванию; поиск по названию, артикулу и номеру без учёта регистра; фильтр по статусу; счётчики по статусам учитывают поиск и остальные фильтры, но не выбранный статус. | |

### HTTP API

| № | Критерий | Тест |
|---|---|---|
| AC-23 | Каждый эндпоинт из раздела «Данные и API» при валидных параметрах отвечает 200, и тело проходит zod-схему контракта из `entities/*`. | |
| AC-24 | Невалидные параметры (дата не в формате `ГГГГ-ММ-ДД`, `from` позже `to`, `to` позже «сегодня», неизвестная площадка или категория, `limit` > 200) → ответ 400 с `{ message }` на русском, без стека и внутренних путей. | |
| AC-25 | Ни один ответ не содержит больше 200 строк заказов: клиент никогда не получает все сырые записи. | |
| AC-26 | `/api/meta` отдаёт список категорий, площадок, «сегодня», время обновления данных и границы доступной истории. | |
| AC-27 | `apiGet` при сетевой ошибке (`fetch` отклонён не из-за отмены) отклоняется с `ApiError` и `status = null`; отмена (`AbortError`) по-прежнему пробрасывается как есть. | |

### Уборка временного

| № | Критерий | Тест |
|---|---|---|
| AC-28 | `/api/health` и `shared/api/health.ts` удалены; временная страница дашборда показывает «работает», когда `/api/meta` ответил, и «недоступен» при ошибке; дымовые тесты (`DashboardPage.test.tsx`, `e2e/smoke.spec.ts`) проверяют это через `/api/meta`. | |

## Состояния

UI в фиче нет, поэтому состояния — на уровне API:
- Загрузка: handlers отвечают с небольшой случайной задержкой (`delay()` MSW: в браузере — «реалистичная», в тестах — почти мгновенная), чтобы будущие виджеты показывали скелетоны.
- Пусто: валидный запрос без данных (например, категория без продаж за период) → 200 с нулями, `null` в долях и пустыми списками, а не ошибка.
- Ошибка: невалидные параметры → 400 (AC-24); неожиданная форма ответа ловит `apiGet` + zod на клиенте (уже есть).

## Дизайн и адаптивность

- Макетов на фичу нет: интерфейса не появляется. Временная страница дашборда меняет только источник проверки «Фейковый API: работает».
- Данные подобраны под макеты: 8 категорий, склады WB (Коледино, Электросталь, Подольск, Казань, Краснодар, Екатеринбург, Тула, Новосибирск) и Ozon (Хоругвино, Пушкино, Гривно, Казань, Новосибирск FBO + склад продавца FBS), названия и артикулы товаров из `reference/*.dc.html` входят в каталог.

## Данные и API

Все эндпоинты — `GET`. Общие параметры фильтров: `from`, `to` (`ГГГГ-ММ-ДД`), `mp` (`all` | `wb` | `ozon`, по умолчанию `all`), `cat` (повторяемый, id категории; нет — все).

| Эндпоинт | Параметры | Что отдаёт |
|---|---|---|
| `/api/meta` | — | категории (id + название), площадки, «сегодня», время обновления, начало истории |
| `/api/kpi` | фильтры | метрики текущего и прошлого периода + sparkline по 14 точек |
| `/api/sales-daily` | фильтры | по дням: WB и Ozon × (выручка, заказы, прибыль) + итог дня прошлого периода |
| `/api/top-products` | фильтры, `sort` (`revenue` \| `orders` \| `buyoutRate` \| `profit`), `limit` ≤ 50 | товар, артикул, площадка, категория, выручка, заказы, % выкупа, прибыль |
| `/api/stocks` | `mp`, `cat`, `status`, `limit` | на дату: товар × склад (FBO/FBS у Ozon), остаток, скорость, дни запаса, статус; счётчики по статусам |
| `/api/orders` | фильтры, `q`, `status`, `sort`, `dir`, `offset`, `limit` ≤ 200 | страница заказов (дата и время, номер, товар, артикул, площадка, склад, сумма, статус), всего найдено, счётчики по статусам |

- Точные поля ответов — zod-схемы в `entities/*` (sale, product, warehouse, marketplace); раскладка схем по слайсам — в реализации, проверяется steiger.
- `mocks/` не импортирует `entities/*` (backend не знает о клиенте); совпадение ответов со схемами доказывают тесты (AC-23).
- Себестоимости в API площадок нет — генератор создаёт её как «справочник продавца» по каждому SKU.
- Фото товаров в API нет: превью в макетах — забота виджетов.

## Безопасность

- **T4** — параметры запросов проверяются zod в handlers, мусор → 400, а не падение (AC-24).
- **T5** — ответы проверяются схемами контракта на клиенте (`apiGet`), это же проверяют тесты (AC-23).
- **T1** — токенов и секретов нет: данные синтетические, реальные API не вызываются.
- Сообщения об ошибках без технических деталей (чек-лист `docs/security.md`).
- Новых зависимостей нет: PRNG пишется сам (несколько строк), даты — встроенный `Date`/`Intl`.

## Не входит в задачу

- Виджеты, хуки TanStack Query, скелетоны и любой новый UI — фичи 3–7.
- Фильтры в URL и их значения по умолчанию — фича 2.
- Web Worker для генерации — только если замер покажет > 100 мс блокировки на запрос (ADR-0004), отдельным решением.
- Экспорт в Excel (фича 8), реальные API WB/Ozon, авторизация.
- Реклама, хранение, штрафы, налоги — в прибыли не учитываются (`docs/domain.md`).

## Замеры

После реализации записать сюда: время первой генерации и время ответа каждого эндпоинта на прогретых данных (`vitest bench`). Цель ADR-0004 — < 100 мс на запрос.

## Решения (согласовано 2026-11-05)

- **История 24 месяца вместо 18** при том же объёме ~100 тыс. заказов: пресет «Год» со сравнением требует 2 года данных. Уточнить ADR-0004.
- **Данные «едут» за реальной датой:** каждый день строится от seed + дата, поэтому одна и та же дата всегда даёт одни и те же заказы (AC-2), а окно истории сдвигается вместе с сегодняшним днём.
- **Порядок коммитов:** одна ветка, три коммита, каждый показывается отдельно: (1) сверка `docs/domain/`; (2) генератор + адаптеры; (3) агрегаторы + handlers + схемы в `entities` + уборка `/api/health`. PR — один, в конце.
