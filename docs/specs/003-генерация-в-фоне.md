# 003. Генерация данных в фоне (Web Worker)

- **Статус:** готово
- **Дата:** 2026-11-06
- **Ветка:** `feat/api-worker`
- **Связанные ADR:** [ADR-0004](../adr/0004-msw-и-генератор-данных.md), [ADR-0010](../adr/0010-контракт-api-и-адаптеры.md), [ADR-0016](../adr/0016-фейковый-backend-в-web-worker.md)

## Цель

Первая генерация ~100 тыс. заказов занимает ~2,7 с ([spec 001](001-фейковый-api.md), «Замеры») и сейчас идёт в основном потоке: всё это время вкладка «замерзает» — не нажимаются кнопки, не крутятся скелетоны. Нужно, чтобы генерация и расчёт ответов шли в фоновом потоке (Web Worker), а интерфейс оставался отзывчивым с первой секунды.

## Как это устроено (простыми словами)

MSW перехватывает запросы `/api/...`, но его обработчики работают в основном потоке вкладки — там же, где React. Поэтому:

1. Логика фейкового backend (проверка параметров, данные, агрегаторы) выделяется в «ядро» — функцию «запрос → статус + JSON», которой не важно, где она работает.
2. В браузере ядро запускается в отдельном Web Worker. Обработчик MSW только пересылает воркеру путь и параметры и ждёт ответ — это микросекунды.
3. Воркер начинает генерацию сразу при старте приложения, не дожидаясь первого запроса: к моменту первого запроса данные уже частично или полностью готовы.
4. В unit- и интеграционных тестах (Node) ядро работает в том же потоке, как сейчас: существующие тесты не меняются.

Контракт API (spec 001) не меняется: те же эндпоинты, параметры, ответы, коды ошибок и тексты.

## Пользовательские сценарии

- Как продавец, я хочу, чтобы дашборд отзывался на клики и показывал анимацию загрузки сразу после открытия, а не замирал на 3 секунды.
- Как разработчик, я хочу, чтобы тесты API работали в Node без воркера и давали те же ответы, что и в браузере.

## Состояния

- Загрузка: пока воркер генерирует данные, запросы ждут; UI показывает свои скелетоны (как сейчас, но вкладка не замирает).
- Пусто: не меняется — определяется ответами API (spec 001).
- Ошибка: падение воркера → 500 с понятным текстом (AC-8); UI показывает своё состояние ошибки.

## Дизайн и адаптивность

- Видимых изменений интерфейса нет. Макеты не затрагиваются.

## Данные и API

- Эндпоинты, параметры и ответы — без изменений (spec 001, spec 002).
- Внутренний протокол основной поток ↔ воркер (не публичный API):
  - при создании: `{ type: 'init', seed, now }` (`now` — число мс);
  - запрос: `{ type: 'request', id, path, search }`;
  - ответ: `{ type: 'response', id, status, body }`.
- Ответы воркера проверяются zod-схемой формы сообщения (`id`, `status`, `body`) — правило «внешние данные через zod»; содержимое `body` проверяют, как и сейчас, схемы в `entities` через `apiGet`.
- Новых зависимостей нет: воркер собирается средствами Vite (`new Worker(new URL(..., import.meta.url), { type: 'module' })`).

## Безопасность

- [security.md](../security.md): CSP не ослабляется (AC-12), секретов нет.
- Сообщения принимаются только от собственного воркера (dedicated worker, тот же домен); форма проверяется zod (раздел «Данные и API»).
- Ошибки по-прежнему без стека и внутренних путей (AC-3, AC-8).
- **zod в режиме `jitless` (найдено тестом AC-12, согласовано 2026-11-06).** zod по умолчанию пробует `new Function`; CSP `script-src 'self'` это блокирует, и браузер записывает нарушение (было и до этой фичи, в основном потоке). `z.config({ jitless: true })` вызывается в модулях `src/app/zodJitless.ts` и `src/mocks/server/zodJitless.ts`, которые подключаются **первым импортом** точек входа `main.tsx` и `api.worker.ts`: настройка читается при создании схем. Новая точка входа обязана сделать то же.

## Замеры

E2E AC-10 (Chromium, собранная версия): от загрузки до ответа `/api/meta` нет задач основного потока длиннее 500 мс; до фичи генерация занимала основной поток ~2,7 с.

## Не входит в задачу

- Изменения контракта API и агрегаторов, ускорение самой генерации.
- Кеширование сгенерированных данных между перезагрузками (IndexedDB и т. п.).
- Индикатор «готовим данные» в интерфейсе — достаточно скелетонов будущих фич.
- Переписывание временной страницы дашборда (это фича KPI-карточек).
