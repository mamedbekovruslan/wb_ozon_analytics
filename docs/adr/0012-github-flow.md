# 0012. Модель веток — GitHub Flow

- **Статус:** заменено [0014](0014-github-flow-с-защитой-main.md)
- **Дата:** 2026-11-04

## Контекст

Один разработчик (пользователь + ИИ), фичи идут последовательно, планируется постоянный деплой на Vercel. Пользователь проверяет каждое изменение перед коммитом и слиянием.

## Рассмотренные варианты

1. Всё в `main` — нет точки проверки перед попаданием в рабочую версию.
2. Git Flow с веткой `dev` — нужен командам с релизами по расписанию; здесь удваивает количество слияний и проверок без пользы.
3. GitHub Flow — `main` + короткие ветки задач, слияние через PR.

## Решение

GitHub Flow:
- `main` всегда рабочая и деплоится на демо;
- на каждую задачу короткая ветка: `feat/…`, `fix/…`, `docs/…`, `chore/…`, `test/…`;
- слияние в `main` через PR (после подключения GitHub) или локально — только с согласия пользователя;
- роль промежуточной проверки выполняют превью-деплои Vercel на каждый PR.

Единственное исключение — первый коммит репозитория (исходный шаблон) сделан прямо в `main`, иначе не от чего создавать ветки.

## Последствия

- Простая история, одна проверка на изменение.
- Если появится команда или реальные пользователи — пересмотреть решение новым ADR (возможно, добавить `dev` или защиту `main`).
