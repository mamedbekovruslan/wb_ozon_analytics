# 0004. Фейковый backend на MSW и детерминированный генератор данных

- **Статус:** принято
- **Дата:** 2026-11-04

## Контекст

Реальных данных и backend нет. Нужно ~100 тыс. заказов, чтобы приложение выглядело как настоящий инструмент. При этом TanStack Query должен работать с настоящими HTTP-запросами (загрузка, кеш, ошибки), а скриншоты и тесты должны быть стабильными.

## Рассмотренные варианты

1. Импорт JSON-файла прямо в компоненты — нет сетевого слоя, TanStack Query бесполезен, огромный файл в репозитории.
2. Отдельный Node-сервер (json-server и т.п.) — лишний процесс, сложнее деплой на статический хостинг.
3. MSW в браузере + генератор на seed — настоящие `fetch`-запросы перехватываются в браузере; работает и в dev, и в демо, и в тестах.

## Решение

- MSW изображает **наш backend (BFF)**, а не API WB/Ozon напрямую (см. [ADR-0010](0010-контракт-api-и-адаптеры.md)).
- Генератор с фиксированным seed (детерминированный PRNG) создаёт данные при первом запросе и кеширует в памяти. Объём: ~100 тыс. заказов за 18 месяцев, ~400 SKU, 8 категорий, ~10 складов, разный профиль WB и Ozon.
- Handlers отдают только агрегаты (KPI, ряды по дням, топ, остатки) и страницы таблиц — никогда все сырые строки.
- Handlers добавляют небольшую случайную задержку, чтобы были видны состояния загрузки.
- Если генерация или агрегация блокирует основной поток дольше 100 мс — выносим в Web Worker (решение по замеру).
- Те же handlers используются в интеграционных тестах.

## Последствия

- Подключение реального backend = убрать MSW; код UI не меняется.
- Данные одинаковы при каждом запуске: стабильные тесты и скриншоты.
- Генерация в браузере тратит время при старте — контролируем бенчмарком (< 100 мс на запрос).
