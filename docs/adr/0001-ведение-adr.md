# 0001. Фиксировать архитектурные решения в ADR

- **Статус:** принято
- **Дата:** 2026-11-04

## Контекст

Проект ведётся с ИИ-агентами, и между чатами контекст теряется. Без записанных решений агент в новом чате может переиграть то, что уже обсуждено, а человек — забыть, почему выбрано именно так. Кроме того, проект портфолио: заказчику важно видеть, что решения принимались осознанно.

## Рассмотренные варианты

1. Ничего не записывать — быстро, но решения теряются и пересматриваются заново.
2. Один общий файл с решениями — быстро разрастается, трудно ссылаться на конкретное решение.
3. ADR (Architecture Decision Records) — один файл на решение, формат MADR.

## Решение

ADR в `docs/adr/`, по одному файлу на решение, по [шаблону](0000-шаблон.md). Нумерация сквозная. Принятые ADR не переписываются: если решение меняется, создаётся новый ADR со статусом «заменяет NNNN», а старый получает статус «заменено». Новый ADR создаётся через skill `new-adr`.

## Последствия

- Любой агент и человек может восстановить причины решений без переписки.
- Новая зависимость или изменение архитектуры требует ADR — это немного замедляет работу, но защищает от случайных решений.
