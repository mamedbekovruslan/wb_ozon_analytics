# 0014. GitHub Flow с защитой ветки `main`

- **Статус:** принято
- **Дата:** 2026-11-05
- **Заменяет:** [0012](0012-github-flow.md)

## Контекст

[ADR-0012](0012-github-flow.md) ввёл GitHub Flow со слиянием через PR, а [ADR-0009](0009-стратегия-тестирования.md) — правило «красный CI блокирует слияние в `main`». Оба держались на договорённости: GitHub позволял запушить в `main` напрямую и влить PR с красными проверками. ADR-0012 допускал и локальное слияние в `main`, а защиту `main` оставлял на будущее.

Теперь CI проверяет каждый PR тремя job: «Поиск секретов (gitleaks)», «Линтеры, unit-тесты, сборка», «E2E (Playwright)». Ошибку агента или случайный push в `main` должна останавливать платформа, а не только внимательность. Разработчик по-прежнему один, поэтому одобрить свой PR сам он не может.

## Рассмотренные варианты

1. **Оставить ADR-0012 как есть.** Плюсы: ничего не настраивать. Минусы: правило из ADR-0009 не проверяется платформой; один неудачный push ломает рабочую версию.
2. **Защита `main` с обязательным одобрением PR.** Плюсы: классическая схема для команд. Минусы: автор не может одобрить собственный PR, поэтому одному разработчику пришлось бы обходить защиту.
3. **Защита `main` без обязательного одобрения, с обязательными проверками CI.** Плюсы: платформа гарантирует PR и зелёный CI; ручную проверку пользователь делает сам перед «ок» (правило 2). Минусы: GitHub не следит за тем, что PR кто-то просмотрел, это остаётся договорённостью.

## Решение

Вариант 3: GitHub Flow из ADR-0012 плюс защита ветки `main` (classic branch protection):
- `main` всегда рабочая и деплоится на демо;
- на каждую задачу короткая ветка: `feat/…`, `fix/…`, `docs/…`, `chore/…`, `test/…`;
- в `main` только через PR, локальное слияние и прямой push запрещены; одобрение PR не требуется;
- обязательные проверки — все три job CI; ветка PR должна быть актуальной относительно `main` (иначе кнопка «Update branch» и повторный CI);
- правила действуют и на администратора (обход запрещён); force push и удаление `main` запрещены;
- слияние PR — только после «ок» пользователя;
- роль промежуточной проверки выполняют превью-деплои Vercel на каждый PR.

Первый коммит репозитория (исходный шаблон) сделан прямо в `main` — единственное историческое исключение.

## Последствия

- Слияние с красным CI и прямой push в `main` технически невозможны, в том числе по ошибке агента.
- Каждое изменение, даже правка документации, проходит полный CI (несколько минут на E2E).
- Если `main` ушла вперёд, ветку PR нужно обновить и дождаться CI заново.
- При переименовании job в `.github/workflows/ci.yml` — обновить список обязательных проверок в настройках репозитория, иначе PR будет вечно ждать проверку со старым именем.
- Если появится команда — пересмотреть решение новым ADR (обязательное одобрение, `CODEOWNERS`).
